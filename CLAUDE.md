## 1. Продукт

Сайт Ольги Грошевой, ИП. Она помогает частным инвесторам купить землю как надёжный актив: подбор участка, проверка рисков (категория, ВРИ, зоны, обременения) и сопровождение сделки, в том числе на банкротных торгах. Работает по всей России.

Аудитория: люди 30–55 лет с накоплениями, которые хотят вложиться в землю, но боятся сложности и обмана.

**Целевое действие посетителя — оставить заявку на бесплатный созвон.** Второе, мягкое действие — получить чек-лист через Telegram-бота. Онлайн-оплата предусмотрена только для одной услуги — проверки участка.

## 2. Тип сайта и страницы

Одностраничный лендинг плюс служебные страницы. Многостраничник, блог и личный кабинет в этой версии не делаются.

### Страницы

| Адрес | Назначение |
|---|---|
| `/` | Лендинг, 14 блоков (ниже) |
| `/thanks/` | Страница после отправки заявки. На неё вешается цель в Яндекс.Метрике |
| `/privacy/` | Политика обработки персональных данных + форма запроса на удаление данных |
| `/oferta/` | Публичная оферта, условия оплаты и возврата |
| `/404.html` | Страница ошибки |
| `/admin/` | Защищённая паролем страница администратора. В поиск не индексируется |

### Блоки лендинга — строго в этом порядке

1. Первый экран: кто и что делает, по всей России, кнопка «Записаться на созвон», три факта мелко
2. «Это про вас, если…» — 3–4 ситуации словами клиента
3. Что я делаю — карточки услуг двух уровней
4. Как проходит работа — 4 шага: созвон → смета до старта → проверка и подбор → сделка
5. Мои сделки в рублях — 5 карточек, чистая прибыль по каждой отдельно
6. Мои сделки в разах — множители ×1,7…×7,1 отдельным блоком
7. Отзывы — 4 реальных скриншота
8. Ольга Грошева — кто она и чем отличается
9. Под какую задачу берусь — 3 сценария + честный блок «с чем не работаю»
10. Сколько стоит — цены + кнопка «Оплатить проверку»
11. Частые вопросы — 6–8 вопросов
12. Не готовы созваниваться — чек-лист через Telegram-бота
13. Форма заявки
14. Подвал: реквизиты ИП, ссылки на политику и оферту, дисклеймер

**Не добавляй страницы, блоки и секции, которых нет в этих списках.** Если кажется, что чего-то не хватает — спроси владельца.

### Чего на сайте не должно быть

Таймеров обратного отсчёта, всплывающих окон, каруселей, счётчиков «осталось 2 места», зачёркнутых старых цен, стоковых фотографий, обещаний доходности.

## 3. Архитектурные принципы

1. **Простота важнее гибкости.** 20 заявок и 5 оплат в месяц. Любое решение, рассчитанное на большее, — ошибка.
2. **Локализация данных первична.** Персональные данные россиян при первичном сборе записываются только на серверы в России (ч. 5 ст. 18 152-ФЗ). Это правило старше соображений цены и удобства.
3. **Минимизация данных.** Собираем три поля. Каждое лишнее поле формы нужно обосновать владельцу.
4. **Юридическая карта побеждает удобство.** При конфликте следуй разделу 9 и сообщи владельцу о конфликте.
5. **Никакой автоматизации без объёма.** Возвраты, подписки, автовыдача доступа делаются руками владельца, пока их единицы.
6. **Сайт правится через Claude Code.** Никаких шагов сборки между правкой файла и живым сайтом.

Фиксированные расходы: около 280 ₽/мес (хостинг при годовой оплате + домен в пересчёте на месяц). Комиссия ЮKassa 2,8 % берётся только с успешных платежей и в фиксированные расходы не входит.

## 6. База данных

Шесть таблиц. Поля с персональными данными помечены **[ПД]**.

### `people` — человек
| Поле | Обязательно | Что это |
|---|---|---|
| id | да | Внутренний номер |
| name | да | Имя **[ПД]** |
| contact_type | да | `phone` или `telegram` |
| contact_value | да | Телефон или ник **[ПД]** |
| source | да | Откуда пришёл: канал, клуб, поиск, прямой заход, метка из ссылки |
| created_at | да | Дата появления |
| deleted_at | нет | Отметка об удалении по запросу |

### `applications` — обращение
| Поле | Обязательно | Что это |
|---|---|---|
| id | да | Номер заявки, показывается в Telegram |
| person_id | да | Связь с `people` |
| service_code | да | Код услуги: `consult`, `check`, `torgi`, `deal`, `zoning` |
| message | нет | Текст задачи **[ПД]** |
| status | да | `new`, `contacted`, `in_work`, `declined`, `done` |
| created_at | да | Время отправки |

### `consents` — согласия
| Поле | Обязательно | Что это |
|---|---|---|
| id | да | — |
| person_id | да | Связь с `people` |
| purpose | да | `processing` (обработка данных) или `marketing` (дайджест). Две разные цели, две разные записи |
| given | да | Дано или нет |
| doc_version | да | Версия текста согласия, с которым человек согласился |
| page_url | да | Страница, где было дано согласие |
| given_at | да | Дата и время |
| revoked_at | нет | Дата отзыва. Запись об отзыве не удаляется — она доказательство исполнения |

### `payments` — платежи
| Поле | Обязательно | Что это |
|---|---|---|
| id | да | — |
| application_id | да | Связь с заявкой |
| provider_payment_id | да | Идентификатор платежа в ЮKassa. **Уникальный индекс** |
| provider_event_id | да | Идентификатор события вебхука. **Уникальный индекс — защита от повторной обработки** |
| amount, currency | да | Сумма и валюта |
| status | да | `pending`, `paid`, `failed`, `refunded` |
| receipt_id | нет | Идентификатор фискального чека |
| created_at, paid_at | да / нет | Даты |

Данные банковской карты не хранятся никогда и ни в каком виде.

### `access_log` — доступ к данным
Кто, когда и какую запись открыл в админке. Обязанность оператора знать, кто имел доступ.

### `dsr_log` — запросы субъектов данных
Обращение об удалении или отзыве: дата получения, тип, дата исполнения, результат. Хранится как доказательство.

### Сроки хранения — утверждены владельцем, подлежат подтверждению юристом

| Что | Сколько |
|---|---|
| Заявки, не дошедшие до оплаты | **6 месяцев** |
| Заявки с оплатой и записи о платежах | **5 лет** (вместе с бухгалтерией) |
| Технические журналы | **90 дней**, дальше удаляются автоматически |
| Записи о согласиях и об их отзыве | Весь срок обработки и после — как доказательство |

## 7. Потоки данных

### 7.1 Отправка заявки
Отправил форму → POST на свой сервер → проверка полей, галки согласия, защита от частых отправок → запись в `people`, `applications`, `consents` → в Telegram уходит номер заявки → переход на `/thanks/`.
**При ошибке:** сообщение «не удалось отправить, напишите в Telegram» со ссылкой, введённые данные остаются в полях. В журнал — только факт сбоя, без содержимого формы.

### 7.2 Просмотр заявки
Вход в `/admin/` по паролю, только по HTTPS → список заявок → смена статуса. Каждый вход и просмотр пишется в `access_log`.

### 7.3 Уведомление в Telegram
Заявка сохранена → сообщение боту: номер заявки, код услуги, время, ссылка на админку.
**Персональных данных в сообщении нет ни при каких условиях.**
**При ошибке:** три попытки с паузой, потом запись в журнал. Заявка уже сохранена, ничего не теряется.

### 7.4 Оплата
Нажал «Оплатить» → запись в `payments` со статусом `pending` → создание платежа в ЮKassa → человек уходит на страницу оплаты ЮKassa → возвращается на `/thanks/`.
Данные карты на наш сервер не попадают.
**Возврат на `/thanks/` не является подтверждением оплаты.** Страница показывает «проверяем оплату, чек придёт на почту».

### 7.5 Вебхук от платёжной системы
POST на `/api/payment-webhook.php` → **проверка подписи** → проверка `provider_event_id` на повтор → смена статуса на `paid` → уведомление в Telegram с номером заявки.
Запрос без корректной подписи отклоняется, в базу не пишется, фиксируется в журнале как попытка подделки.
Повторная доставка того же события ничего не меняет: сервер отвечает «принято» и выходит.

### 7.6 Фискальный чек
Платёж прошёл → «Чеки от ЮKassa» формируют чек → чек уходит в налоговую через ОФД и покупателю → у нас сохраняется только `receipt_id`.
**При ошибке:** чек не сформирован — решается в тот же день через поддержку ЮKassa, потому что чек обязан быть сформирован в момент расчёта.

### 7.7 Оплата прошла, вебхук не пришёл
`reconcile.php` раз в сутки опрашивает ЮKassa по всем платежам в статусе `pending` → находит фактически оплаченные → доводит статус → уведомление «расхождение устранено».
Если и это не сработало — платёж виден в админке в отдельном списке «требуют внимания». Ни один платёж не пропадает молча.

### 7.8 Платёж не прошёл или возвращён
Отказ → вебхук со статусом отмены → статус `failed` → человек видит «оплата не прошла» и кнопку повторить. Заявка сохраняется.
**Возврат инициирует владелец в личном кабинете ЮKassa, не сайт.** Приходит вебхук → статус `refunded` → чек возврата формирует ЮKassa. Автоматических возвратов по кнопке на сайте нет.

### 7.9 Запрос на удаление данных
Обращение через форму на `/privacy/` или на почту → проверка личности заявителя → удаление в админке → затирание `name`, `contact_value`, `message` → запись в `dsr_log` → ответ человеку.
**Срок ответа — 10 рабочих дней. Уничтожение при отзыве согласия — 30 дней.**
Остаётся обезличенное: номер заявки, дата, сумма. Если данные нужны для бухгалтерии по оплаченной услуге — полное удаление невозможно, и владелец обязан письменно объяснить причину со ссылкой на срок хранения.

### 7.10 Отзыв согласия на рассылку
Отписка → снимается флаг у записи `consents` с целью `marketing`, проставляется `revoked_at`.
**Отзыв согласия на рассылку не удаляет заявку.** Это разные цели обработки.

Личного кабинета в этой версии нет, поэтому регистрации, входа, восстановления доступа и выдачи доступа после оплаты не существует.

## 9. Юридические требования в реализации

Проверено 4 сентября 2026. Продавец — ИП в России, аудитория и платежи только российские. **GDPR и законы США не применяются.**

### Обязательно реализовать

1. **Два независимых чекбокса** у формы: согласие на обработку данных и отдельно согласие на дайджест. Оба не отмечены заранее. Отправка без первого заблокирована.
2. **Согласие оформляется отдельно**, а не встраивается в пользовательское соглашение или оферту — требование действует с 1 сентября 2025.
3. **Фиксация согласия**: версия текста, дата, время, адрес страницы.
4. **Cookie-баннер** с категориями и возможностью отказа, со ссылкой на политику. **Яндекс.Метрика не загружается до получения согласия.** Формулировка «продолжая пользоваться сайтом, вы соглашаетесь» не используется.
5. **Страницы документов**: политика обработки данных, оферта, «спасибо», 404.
6. **Реквизиты ИП в подвале**: Ф. И. О., ОГРНИП, ИНН, адрес для обращений, телефон, email.
7. **Механизм отзыва согласия и удаления данных** с соблюдением сроков: ответ 10 рабочих дней, уничтожение 30 дней.
8. **Автоматическое удаление** заявок и журналов по истечении сроков из раздела 6.
9. **Первичная запись персональных данных — только на сервер в России.**
10. **Дисклеймер** рядом с блоками кейсов: результаты прошлых сделок не гарантируют будущих. Обещать доходность запрещено.

### Владелец делает вне сайта

Подаёт уведомление в Роскомнадзор **до начала обработки данных** (ст. 22 152-ФЗ; штраф для ИП 100 000–300 000 ₽). Назначает ответственного за обработку. Заключает договоры с обработчиками: хостинг, ЮKassa. Ведёт внутренние документы оператора. Отвечает на запросы субъектов. При запуске рекламы — регистрируется в ОРД и маркирует креативы (штрафы 200 000–500 000 ₽).

### Требует юриста

Тексты политики, согласий и оферты. Вопрос, обязательна ли оферта именно для этих услуг. Достаточность cookie-баннера в текущей конфигурации. Формулировка отказа от гарантий доходности. Подтверждение сроков хранения.

## 10. Безопасность

- Собираем три поля. Новые поля формы — только с разрешения владельца.
- Админка закрыта паролем, отдана только по HTTPS, закрыта от индексации. Формы «забыли пароль» нет — восстановление через панель хостинга.
- Каждый доступ к персональным данным пишется в `access_log`.
- Вебхук: обязательная проверка подписи; запрос без подписи отклоняется.
- Повторная доставка вебхука обрабатывается через уникальный индекс `provider_event_id`.
- Ограничение частоты отправки формы: не чаще трёх раз в минуту с одного адреса.
- Все запросы к базе — только через подготовленные выражения.
- Вывод пользовательского текста в админке экранируется.
- Резервные копии: ежедневные на стороне хостинга плюс ручной экспорт владельцем раз в месяц.

## 11. Деплой

- Сайт выкладывается: содержимое `public/` на виртуальный хостинг в России.
- База: MySQL на том же хостинге.
- Секреты: `private/config.php` вне публичной директории, в репозиторий не попадает.
- Резервные копии: ежедневные автоматические на стороне хостинга; хранятся там же.
- Проверка восстановления: владелец раз в квартал скачивает бэкап и убеждается, что файл открывается и данные на месте.
- `reconcile.php` запускается по расписанию хостинга раз в сутки.
- `moodboard/` и `docs/` на хостинг не выкладываются.

Ручные действия владельца: покупка и продление домена, договор с ЮKassa, подача уведомления в Роскомнадзор, установка счётчика Метрики, ежемесячный экспорт данных.

## 14. Правила для ИИ-сборщика

Эти правила действуют в каждой сессии сборки.

1. **Не меняй стек** — фронтенд, PHP, MySQL, хостинг, платёжную систему — без явного разрешения владельца.
2. **Не добавляй библиотеки, фреймворки и внешние сервисы** без необходимости и без разрешения. Любой новый сервис сначала проверяется на то, где он хранит данные.
3. **Не добавляй страницы, блоки и поля форм**, которых нет в разделе 2.
4. **Не выдумывай тексты, цены, кейсы, отзывы, юридические формулировки и реквизиты.** Вместо отсутствующего содержимого ставь понятный маркер `TODO:` с описанием, что именно нужно от владельца.
5. **Не храни секреты в коде и репозитории.** Только имена переменных из раздела 8.
6. **Не выводи секреты в журналы** ни при отладке, ни при ошибках.
7. **Не отправляй персональные данные в Telegram.** Только номер заявки, код услуги, время, ссылка.
8. **Не включай необязательную аналитику до получения согласия.**
9. **Не меняй правила хранения и удаления данных** из разделов 6 и 9.
10. **Не считай платёж состоявшимся на основании страницы «успешно».** Только подтверждение от платёжной системы.
11. **Всегда проверяй подпись вебхука.**
12. **Всегда учитывай повторную доставку вебхука** — обработка должна быть безопасна при повторе.
13. **Не считай задачу выполненной без проверки ошибок и пограничных сценариев**: пустая форма, отказ платежа, недоступная база, потерянный вебхук, повторная отправка.
14. **При конфликте удобства и юридической карты следуй карте** и сообщи владельцу о конфликте.
15. **При отсутствии критически важного решения остановись и спроси**, а не угадывай. Это касается сроков хранения, текстов документов, цен и реквизитов.
16. **Не редактируй этот файл** без явного разрешения владельца.

### Отдельно про дизайн

**Дизайн-система на момент написания не утверждена — владелец разрабатывает её заново.**
Мудборд в `moodboard/index.html` носит справочный характер и не является утверждённой системой.

Пока владелец не передал дизайн-систему, **не выбирай самостоятельно** цвета, шрифты, знак, сетку, радиусы и отступы. Верстай структуру и логику, оставляя визуальные решения маркерами `TODO:`. Когда система будет передана — она становится обязательной, и при конфликте с мудбордом побеждает она.
